### ⚠️ 踩坑：ntfy 推送的 header 编码

两个坑都实测踩过：

1. **HTTP header 只能承载 latin-1**。用 `requests.post(..., headers={"Title": "✅ 图片生成完成"})` 会抛
   `'latin-1' codec can't encode character '\U0001f514'`。
   **解法**：header 值传 **bytes**（`str(x).encode("utf-8")`），requests 会原样发送 UTF-8 字节，服务端正常解析。

2. **ntfy.sh 不解析 `application/json` 请求体**。用 `requests.post(url, json=payload)` 时，
   ntfy 会把整个 JSON 字符串当成 message 文本，title/tags/click 全部丢失。
   **解法**：改回 `data=message.encode("utf-8")` + `Title`/`Tags`/`Click` header（bytes 形式）。

验证方式：`curl "https://ntfy.sh/<topic>/json?poll=1&since=1m"`，确认 title/tags/click 三个字段被正确解析。

### 其他要点

- `get_user_id()` 未登录时会**自动创建匿名用户**，不能用于私有配置接口（会污染匿名用户数据），
  故新增 `_get_session_user_id()`：未登录返回 None，配合 401 响应。
- 主题保存前统一 `strip().lstrip("/")`，用户填 `/topic` 也能正常工作。
- 主题为空时跳过推送（不报错）。
- DB 实际路径是 `data/history.db`（不是 `data/app.db`，后者是0 字节空文件）。

## 步数输入框改为可输入+下拉（datalist）

### 做法

`static/index.html` 里把 `<select id="steps">` 换成 `<input type="number" list="stepsOptions">` + `<datalist>`。
这是「既能下拉选、又能自由输入」的标准方案 —— datalist 挂在 input 上时，浏览器显示下拉箭头，
点选填值，同时允许直接键入列表外的任意数字。

```html
<input type="number" id="steps" value="8" min="1" max="100" step="1"
       list="stepsOptions" placeholder="可下拉选择或直接输入">
<datalist id="stepsOptions">
    <option value="8"></option> ... <option value="20"></option>
    <option value="30"></option> <option value="40"></option>
</datalist>
```

配套改动：
- `generateImage()`：加范围校验 `steps < 1 || steps > 100` 时alert 提示（原来只有 `|| 8` 兜底）。
- `loadSavedValues()`：从 localStorage 恢复时校验 `savedSteps >= 1 && <= 100`，非法回落到 8。
- CSS：`.form-group input:focus` 补上 `input[type="number"]:focus`（原来漏了number，边框不变色）；
  加 `.form-group input[type="number"][list] { cursor: pointer; }`。

### 注意

- `saveValues` / `loadSavedValues` 里 `document.getElementById('steps').value` 写法不变，
  select 和 input 都支持 `.value`。
- 事件绑定 `['prompt','seed','steps',...].forEach` 加的是 `change` + `input`，input 元素天然支持，无需改。
- SW (`sw.js`) 只缓存 `.png/.jpg` 等图片，**不缓存 HTML**，所以改前端不需要动 SW 版本号，
  也不用担心用户拿到旧页面。

# Draw Things HTTP API 调研结论（2026-10-11 上午）

## 官方文档状态

| 渠道 | HTTP API 参数文档 |
|---|---|
| drawthings.ai 官网 | 无（纯产品页）|
| wiki.drawthings.ai（社区维护、官方背书）| 无，站内搜 "API server txt2img" 零结果 |
| draw-things-community 仓库 | 无 HTTP 部分 |
| **gRPC** | **有**（FlatBuffers + protobuf 编进开源客户端库）|

**结论：官方只文档化了 gRPC，HTTP API 从未正式文档化。**

## HTTP 端点实测（本机 7888）

机制 = **根路径返回全量配置 JSON（87 字段）= 参数的唯一真相**。

- `GET  /` → 完整配置 JSON（这也是项目里读 seed 的方式）
- `POST /sdapi/v1/txt2img` → 传同名字段即覆盖，未传的保持画布当前值

**不存在的端点**（全部 404 或 fallback 到 `/`）：
`sdapi/v1/options`（返回的字节与 `/` 完全相同，MD5 一致，实为 SPA fallback）、
`img2img`、`progress`、`status`、`sd-models`、`samplers`、`upscalers`。

**参数名坑**：社区资料都写 `cfg_scale` / `sampler_name`，**实测 Draw Things 用的是
`guidance_scale` 和 `sampler`**，A1111 风格别名不生效。

## gRPC 能力（权威来源：drawthingsai/draw-things-comfyui 仓库）

`ImageGenerationService`：`GenerateImage`(服务端流式)、`FilesExist`、`UploadFile`(双向流)、`Echo`、`Pubkey`、`Hours`
`ControlPanelService`：`manageGPUServer`、`updateThrottlingConfig`、`updatePem`、`updateModelList`

参数走 FlatBuffers `GenerationConfiguration`（86 字段），gRPC 独有的 4 个能力：
1. `hints[]` ControlNet/参考图（depth/canny/pose/inpaint/shuffle）
2. LoRA 分段加载（`mode`: all/base/refiner）
3. 进度流（`currentSignpost`: textEncoding → sampling(step) → imageDecoded）
4. 中间预览（`previewImage` 流式返回）

**最大门槛**：图片用 `DTTensor` 私有格式（68 字节头 + float16，范围 [-1,1]），
服务端**不接受 PNG/JPEG**。
- 解码：`uint8 = clamp((f16 + 1) * 127, 0, 255)`
- 编码：`f16 = (uint8 / 127) - 1`
- 头部前 9 个 uint32：`[0..5]=标志位, [6]=height, [7]=width, [8]=channels`

## 踩坑记录（都是实际卡住的）

### 1. flatc 不必用brew，但必须下macOS 版
- `brew install flatbuffers` 在沙箱里失败（`Operation not permitted @ apply2files`）
- flatc **不是** pip 包，只能从release 下载。
  资产名是 `Mac.flatc.binary.zip`（Apple Silicon），**不是** `macos.flatc.binary.zip`（404）。
  下载地址前缀 `https://ghproxy.net/https://github.com/google/flatbuffers/releases/download/v24.3.25/Mac.flatc.binary.zip`
  → 解压后 `/tmp/flatcm/flatc --version` 可用。
- 必须加 `--gen-object-api`，否则不生成 `GenerationConfigurationT`，没法构造写入。

### 2. 纯 Python flatbuffers 库没有 CreateVector
手工 `StartVector/PrependUOffsetTRelative` 构建 LoRA 向量需要 hack Builder 内部（`Bytes`/`head`），
极易出错且无法验证。**结论：老老实实用 flatc 生成代码。**

### 3. 生成代码的扁平导入会炸
`protoc` 和 `flatc` 生成的代码都是 `import imageService_pb2` / `from LoRA import LoRA`，
放在包内直接报 ModuleNotFoundError。且 **FlatBuffers 的延迟导入在函数体内**，
正则要匹配任意缩进（`^\s+import X`），只改行首会漏。
已在 `scripts/gen_proto.sh` 里用 Python 批量修复。

### 4. Builder 调用顺序有严格约束
- `PrependXxxSlot` 必须在 `StartObject()` **之后**、`EndObject()` 之前
- `Finish()` 参数是 `builder.Offset()`，**不能传 `builder.Output()`**（会抛 BuilderNotFinishedError）
- `Output()` 只能在 `Finish()` 之后调用

### 5. flatc 生成的读写类命名不对称（最容易debug 地狱）
- 读取类 `GenerationConfiguration`：方法**大写**开头 —— `cfg.StartWidth()`、`cfg.Loras(i)`
- 修改类 `GenerationConfigurationT`：属性**驼峰** —— `cfg.startWidth`、`cfg.loras`
写 `cfg.StartWidth = 8` 不报错但**静默无效**，配置变成 12 字节空壳。
批量改正则时要用 `dir(T对象)` 拿合法字段名做校验，别硬编码。

### 6. 沙箱网络
- `raw.githubusercontent.com` 直连不通；`ghproxy.net` 可用（也可直接 `git clone https://ghproxy.net/...`）
- `api.github.com` 搜代码需认证（401），但列 release 资产可以
- `ps` 命令不可用，用 `lsof -ti :端口`

### 7. gRPC 客户端会走系统代理
环境里有 `HTTP_PROXY=http://127.0.0.1:60823`，gRPC 会自动读取并尝试走代理，
连接本地服务会失败（报`ipv4:127.0.0.1:54008: HTTP proxy...`）。
**解决**：channel 加 `grpc.enable_http_proxy=0` 选项，或用
`grpc.insecure_channel` 时显式传`options=[("grpc.enable_http_proxy", 0)]`。

## FlatBuffers 关键约束

`start_width` / `start_height` 是 **ushort，存储时除以 64**（512 → 8）。
不转换服务端尺寸全错。这是最容易踩的坑。

## gRPC 联调：关键突破与踩坑（补记）

### ✅ 已验证跑通的部分

- **端口 7888 同时跑 HTTP 和 gRPC**（Draw Things 的 API Server 就是这个端口）
- **Echo 成功**：`HELLO DrawThingsWebUI`，返回 36 个模型文件列表
- **TLS 用官方内置 CA**：`src/drawthings_ca.py`（从 draw-things-comfyui/src/credentials.py 抄的）

### ⚠️ 最大的坑：TLS 信任根不能用抓来的服务端证书

**错误做法**：用 socket 抓服务端证书当 `root_certificates`。
**后果**：握手**静默挂起**—— 没有 CERTIFICATE_VERIFY_FAILED，
没有任何 TLS 错误日志，只表现为 `DEADLINE_EXCEEDED` / `FD shutdown`，
排查时完全看不出是证书问题（我为此绕了半小时，误以为是并发/服务端忙）。

**正确做法**：用 Draw Things 的 Root CA（`CN=Draw Things Root CA`），
官方在 draw-things-comfyui/src/credentials.py 里硬编码了这份，已复制到 `src/drawthings_ca.py`。

配套：`ssl_target_name_override = "localhost"`
（服务端证书 `CN=localhost`，SAN 含 localhost 与 127.0.0.1；我一开始猜"drawthings" 报
`Peer name drawthings is not in peer certificate`）。

### ⚠️ 第二个坑：Draw Things 是单任务串行，客户端超时会把服务端堵死

我第一次给 GenerateImage 传了 280s 超时但**客户端先放弃**（或服务端响应慢），
此后服务端就一直不响应新的 TLS 握手，连 Echo 都 DEADLINE_EXCEEDED。

**症状**：TCP 能连（`create_connection` 成功）但 `wrap_socket` 握手超时。
**这不代表服务没开**，而是它正忙/卡死。

**对策**（已写入代码）：
- `backend.generate_image_with_retry(retries=2, retry_delay=5)`
- 客户端超时不要设太短；一次失败后先等几秒再重试
- `is_available()` 在 UNAVAILABLE/DEADLINE_EXCEEDED 时改用裸 TLS 握手探测，
  避免把"服务端忙"误判成"gRPC 未开启"而错误降级到 HTTP

### ⚠️ 第三个坑：异常分类错了会连锁误降级

`echo()` 原本把所有 `grpc.RpcError` 包成 `GrpcUnavailableError`，
导致调用方分不清"连不上"和"服务端忙"。已改为原样抛出，
只在 `UNAVAILABLE`/`UNIMPLEMENTED` 时才算不可达。

### 沙箱网络探测注意

- `timeout` 命令和 `curl --noproxy` 判端口会误报（沙箱干扰）。
  可靠方式：`./venv/bin/python` + `socket.create_connection` 显式探测。
- `ps` 不可用，用 `lsof -ti :端口`。
- gRPC 必须加 `grpc.enable_http_proxy=0`，否则走 HTTP_PROXY 连不上本地。

`/tmp/flatcm/flatc`（Mac.flatc.binary.zip 解压）。沙箱重启后会丢，

## 第二次联调（重启后）：定位到真正的边界

### 已确认

- **7888 只跑 gRPC**：改协议后 HTTP 根路径也超时了（ReadTimeout），
  说明 HTTP server 被关掉，端口只剩 gRPC。所以 HTTP 降级通道在当前配置下**不可用**。
- **Echo 在服务端空闲时成功过**：`HELLO DrawThingsWebUI`。整条链路（TLS+HTTP2+protobuf）验证通过。

### 症状规律（重复出现，值得记住）

```
[0] 20.01s DEADLINE_EXCEEDED     ← 首次 RPC，握手等满超时
[1]  0.00s UNAVAILABLE: FD shutdown  ← 同一 channel 后续调用立即失败
```

- 裸 `ssl.wrap_socket`（不带 ALPN）有时能秒通；
- 带 `set_alpn_protocols(['h2'])` 或走 gRPC 则握手挂满超时。
- `GRPC_TRACE=handshaker` 显示：`tcp_connect` 与 `http_connect` 都 OK，
  **卡在 `security` handshaker**（TLS 层没完成）。

### 结论

Draw Things gRPC 服务端对**连接频率/并发很敏感**（单任务串行）。
反复用短超时重试会持续触发 TLS 握手失败，形成"越试越不通"的负循环。
正确做法是**等它彻底空闲后再发一次请求**，而不是密集重试。

### 代码层面已做的修正

1. `is_available()` 改为**必须真实 Echo 成功**才算可用。
   之前退化成"裸 TLS 能握手就算可用"是错的 —— 那只能证明端口在监听，
   不能证明 gRPC 服务能应答，会导致误判并错误降级到 HTTP。
2. 新增 `wait_until_idle(max_wait, interval)`：用裸 TLS 握手轮询等待服务端空闲
   （可作为"是否可发请求"的前置门），但**不能**用它替代 Echo 判定。
3. `channel` 失败后需 `close()` 并新建，gRPC 不会自动重连到已死的 channel。
4. 删除废弃的 `fetch_server_certificate`（内置 CA 才是正解，留着会误导）。

### 下一步（需要用户配合）

服务端空闲后**一次性**发生图请求（不要前置Echo、不要密集重试），
观察能否拿到 DTTensor 流。若仍失败，则 Draw Things gRPC 侧可能有其它限制
（如需要共享密钥 sharedSecret，或该版本 HTTP/2 有兼容问题），需要换思路。

## ⚠️ 事故记录：我把用户的电脑搞卡死了

**经过**：为调试 gRPC，10 分钟内连续发起约 8-10 次生图请求（256x256/4步）。
结果 `load average` 冲到 **9.92**，内存 free 只剩 92MB，`Pageouts` 470 万次，
**整机卡死，Draw Things 也死机**（进程在、端口在监听，但 TLS 握手永久超时）。

**根因**：
1. Draw Things **单任务串行** —— 每个请求都要排队。
2. 客户端超时后**连接仍占着服务端队列**，不释放。
3. 我还在超时后**自动重试**（`retries=2`），队列越堆越长。
4. `max_receive_message_length` 设了 256MB，多进程各持大 buffer。
5. 模型是 `qwen_image_2.1_i4x.ckpt`（大模型），单次推理内存开销本就高。

**教训（写进代码约束）**：
- 生成超时从 900s 降到 **300s**（实测 256x256/4步 约 90s，留 2 倍余量即可）
- `max_receive/send_message_length` 从 256MB 降到 **128MB**
- `generate_image_with_retry` 默认 `retries=0`（**不重试**）——
  宁可本次失败让用户手动重试，也不要自动堆积请求把服务端拖死
- 新增参数上限校验：尺寸 ≤ 4096、步数 ≤ 150（**本地拦截**，不消耗服务端资源）
- keepalive 放宽到 120s，且 `permit_without_calls=0`（少发 ping）

**新增诊断工具** `scripts/grpc_doctor.py`：
只发轻量 Echo，不发生图，三段式输出 TCP / TLS / gRPC 各自状态并给出诊断建议。
联调前先跑它确认服务可用，避免无谓的生图请求把机器压垮。

```bash
python scripts/grpc_doctor.py              # 默认 7888
python scripts/grpc_doctor.py --port 7859 --timeout 30
```

**给用户的教训**：调试第三方本地服务（尤其单任务串行的推理服务）时，
不要密集重试；先做轻量健康检查，确认可用再发重请求。

## 如何判断 Draw Things 是否空闲（实测确定）

**关键结论：TCP 能连 ≠ 空闲。TLS 握手完成才是空闲判据。**

实测对比（Draw Things 正在生成时）：

| 探测方式 | 结果 | 能否判空闲 |
|---|---|---|
| `socket.create_connection` | **永远秒通** | ✗ 内核 accept backlog 有缓冲，不代表应用层有空 |
| `ssl.wrap_socket`（1.5s 超时）| 挂起至超时 | ✓ 需要应用主线程参与 |

空闲时 TLS 握手 <100ms 完成。

**原理**：Draw Things 单任务串行，生成时不接受新连接。
TLS 握手要经过应用主线程，所以忙时必然卡住；而 TCP 层只是内核缓冲区，
来一个 SYN 就应答，不需要应用参与。

**安全**：该探测只做 TLS 握手，**不发任何 RPC**，不给生成中的任务加负担，
可安全高频调用。这正是之前我"用生图请求探测空闲"的做法所缺失的。

新增工具 `scripts/wait_idle.py`：
```bash
python scripts/wait_idle.py --once           # 查一次
python scripts/wait_idle.py                  # 等到空闲（最长 5 分钟）
python scripts/wait_idle.py --watch          # 持续监控
```

客户端新增 `DrawThingsGrpcClient.is_idle() -> (bool, str)` 与
`wait_until_idle(max_wait, interval)`。

**流程规范**：生图前先 `is_idle()` → 不空闲则 `wait_until_idle()` →
确认空闲后才发生图请求。禁止用生图请求本身去探测空闲。

```python
img = np.clip((arr + 1) * 127.5, 0, 255).astype(np.uint8)
```

## ⚠️ 修复前端"服务器连接失败 415"（19:35）

用户截图：前端报 **`服务器返回状态码: 415 (http://127.0.0.1:7888)`**。

### 根因
- **7888 现在是纯 gRPC 端口**（无论明文还是 TLS），**任何明文 HTTP/1.1 请求都被 gRPC server 以 415（Unsupported Media Type）拒绝**。实测 `GET /`、`GET /sdapi/v1/options`、`POST /sdapi/v1/txt2img` **全部 415**。
- `app.py` 的 **`GET /api/status`（check_status）仍直连 HTTP** 探测 `/sdapi/v1/options` → 拿到 415 → 返回 `success:false` → 前端弹"服务器连接失败 / 配置服务地址"。而 `/api/generate` 早已改走 backend（auto→gRPC），所以生图其实是好的，只是**连接检测误报**。
- 附带发现：`is_available()` 首次冷启动可能误判 False（timeout 偏短），会导致 auto 错误降级到 HTTP。

### 修复
- `app.py` `check_status`：**通道感知**。当 `drawthings_channel` 为 `grpc`/`auto` 时，用 `backend.is_grpc_available(force_check=True)` 探测（**冷启动重试 2 次**），可用即返回 `success:true, raw_data.channel="grpc"`；`model` **留空**（gRPC 无"当前画布模型"概念，之前误把 `override.models[0]` 这个 dict 当模型名，前端 `escapeHtml(data.model)` 会显示 `[object Object]`）。
- `backend.is_grpc_available`：探测 timeout `5→8s`，减少冷启动误判。
- 重启 Flask 服务验证：`GET /api/status` **冷启动首次即返回 `{"success":true,...}`**。

### ✅ 修复「切回 gRPC 后 WebUI 报 415」（10-12 04:40）

**现象**：切回 gRPC 协议后 WebUI 报 `DrawThings API 返回状态码: 415`（415 = HTTP 打到纯 gRPC 端口）→ 说明 auto 走了 HTTP。

**根因（两层，都修了）**：
1. `backend.generate_image_auto` 的 auto 分支用 `is_grpc_available()` 预判；该探测**冷启动会误判 False** → 直接降级 HTTP → 415。
2. 更深：`grpc_client.echo` / `generate_image` 的 TLS 自动协商**只对 `UNAVAILABLE` 翻转 use_tls**；而服务端对"协议不匹配"的请求（TLS 打到明文 gRPC）是**挂起到超时 → `DEADLINE_EXCEEDED`**，协商不触发 → 永久失败。（实测：新 client `use_tls=True` 连续两次 DEADLINE(8s)，第三次才偶然变 False 成功。）

**修复**：
1. `grpc_client.py`：`echo` 与 `generate_image` 的协商条件扩展为 `UNAVAILABLE` **+** `DEADLINE_EXCEEDED`（首次失败即翻转 use_tls 重试一次）。
2. `backend.py` `generate_image_auto`：**auto 模式不再预判**，改为「**直接先试 gRPC，失败再降级 HTTP**」，彻底消除冷启动误判。

**验证**：
- `/api/status` → `{"success":true, "raw_data":{"channel":"grpc"}}`
- 端到端 `POST /api/generate`（`model=qwen_image_2.1_turbo_q6p.ckpt`，推荐表自动补 1024/CFG1/Euler a Trailing）→ **`success:true`，出图 247s**，存 `data/generated_images/generated_20261012_043950.png`（橘猫，质量好）。

**备注**：当前服务端 gRPC 是**明文**（`use_tls=False` 才通），而 config `grpc.use_tls=true` → 首次探测会浪费一个 timeout(8s) 自愈，之后同 client 复用即快。生产无碍，但可考虑把 config `use_tls` 设为与实际一致以省掉首次 8s。

### ✅ 基础版偏色根因找到并修复：4 通道 ARGB 解码 bug（10-12 10:14）

**排查过程**：打印 DTTensor 头部 channels 发现 ——
| 模型 | 图块 channels | 结果 |
|---|---|---|
| Qwen **Turbo** | **3（RGB）** | 正常 ✅ |
| Qwen **基础版** | **4** | 偏色 ❌ |

切片对比（同一张 4 通道图）：
- `[0:3]`（旧代码）→ 苹果过曝偏橙、整片洋红（= 那个「没颜色」）
- **`[1:4]`** → **完美正确**（红苹果/热气球蓝天绿草）

**根因**：Draw Things 的 4 通道格式是 **ARGB（alpha 在第一个通道）**，正确 RGB 是**后 3 个通道**；旧代码取前 3 个，把 alpha 当成了 R 通道 → 整片偏色。基础版原生支持透明（返回 4 通道）故命中，turbo 返回 3 通道不受影响。

**修复**：`dt_tensor.dt_tensor_to_rgb_array` —— `channels==4` 时取 `[:, :, 1:4]`（原为 `[0:3]`）。

**验证**：基础版 40 步 → **彩色热气球/蓝天/绿草**（`data/qwen_base_fixed.png`；端到端 `data/generated_images/generated_20261012_101438.png`）。**基础版现已完全可用。**

### 修复历史记录「部分提示词点击无法复制」（10-13 09:17）

**根因**：`static/history.html` 把提示词**内联进 onclick 的 JS 字符串**：
```js
onclick="... copyToClipboard('${escapeHtml(item.prompt)}', '提示词')"
```
而 `escapeHtml`（用 `div.innerHTML`）**只转义 `<>&`，不转义单引号**。所以提示词含 `'`（或换行/反斜杠）时 JS 字符串断裂 → onclick 抛错 → 复制失败。这就是「**部分**提示词无法复制」。

**修复**（不再内联任意文本到 onclick）：
- 提示词：`onclick="... copyText(this, '提示词')"`，新增 `copyText(element,label)` 从 `element.textContent` 取**原文**。
- Seed 同样改为 `copyText(this,'Seed')`。
- Tooltip：`showPromptTooltip(this)`，函数内用 `element.textContent`（顺带修掉原先把 HTML 实体当文本显示的瑕疵）。

**校验**：history.html 内联 JS `node --check` 通过。**纯静态改动，无需重启**（SW 只缓存图片，不缓存 HTML）。
